## 3️⃣ HTTP状态码问题

### 问题位置：fetch.py:165 `fetch_url_content_resilient`

```python
def fetch_url_content_resilient(url: str, timeout: int) -> tuple[str, str]:
    try:
        return fetch_url_content(url, timeout), url
    except HTTPError as exc:
        fallback_url = remove_review_true(url)
        if exc.code >= 500 and fallback_url != url:  # ← 只处理5xx错误！
            return fetch_url_content(fallback_url, timeout), fallback_url
        raise  # ← 401会被re-raise
```

**为什么这是问题**：
- review端点返回 HTTP 401
- 条件 `exc.code >= 500` 不成立（401 < 500）
- 所以 `raise` 异常
- 调用端的 `except Exception` 捕获它
- 最终没有caibiao_text

## 4️⃣ 真正的根本原因猜想

经过分析，最可能的原因链：

```
1. newGbInfo页面通常不包含采标信息
   ↓
2. 代码需要fallback到review页面
   ↓
3. review页面返回 HTTP 401 (65%的情况)
   ↓
4. HTTPError异常被抛出
   ↓
5. 多线程中的except Exception捕获
   ↓
6. log显示 "continue" (跳过该hcno)
   ↓
7. 没有找到任何采标信息
   ↓
8. ws.cell() 写入空字符串
   ↓

```

**为什么是多线程的问题**：
- 单线程时可能只测试了1-2个URL，可能碰巧那些URL没有fallback
- 多线程时256个URL全部跑，fallback逻辑暴露了真实问题
- 前面的诊断脚本只测了newGbInfo端点，没测review fallback

## 6️⃣ 修复方案

### 方案1：添加HTTP 401重试机制（推荐）

```python
def fetch_url_content_resilient(url: str, timeout: int, max_retries: int = 3) -> tuple[str, str]:
    for attempt in range(max_retries):
        try:
            return fetch_url_content(url, timeout), url
        except HTTPError as exc:
            fallback_url = remove_review_true(url)
            
            if exc.code == 401 and attempt < max_retries - 1:
                # 对401重试
                wait_time = 2 ** attempt  # 1s, 2s, 4s
                print(f"[RETRY] Got 401, waiting {wait_time}s before retry {attempt+1}/{max_retries}")
                time.sleep(wait_time)
                continue  # ← 再试一次
            
            if exc.code >= 500 and fallback_url != url:
                return fetch_url_content(fallback_url, timeout), fallback_url
            
            raise
```
